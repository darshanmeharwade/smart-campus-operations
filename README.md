# Smart Campus Operations

Smart Campus Operations is a Flask web application for coordinating common campus facility workflows in one place. Students can find rooms and equipment, request bookings, and report facility issues. Administrators can review requests, manage reports, and monitor operational activity through a dashboard.

The project is designed as a lightweight campus operations MVP and hackathon demonstration. Its issue recommendations are transparent keyword rules, not machine-learning predictions.

## Live demo and repository

- **Live demo:** [https://smart-campus-operations.vercel.app](https://smart-campus-operations.vercel.app/)
- **GitHub repository:** [darshanmeharwade/smart-campus-operations](https://github.com/darshanmeharwade/smart-campus-operations)

## Features

### Student and account workflows

- Sign in with a database-backed identifier and password.
- Create a student account with a name, any non-empty identifier (up to 254 characters), and a password of at least eight characters. The server assigns the `student` role; public signup cannot create administrator accounts.
- Browse active rooms and equipment, filter by resource type, and check availability for a requested date and time.
- Submit booking requests, view personal bookings, and cancel eligible bookings.
- Submit facility reports with a title, description, location, and category; students see their own reports.

### Administrator workflows

- View pending booking requests and approve or reject them.
- Review facility reports, update report status, and save a separate administrator triage category and priority.
- View booking and issue totals, status/category counts, and top facilities. Analytics can be filtered by date.
- Use role-protected administrator pages and actions.

### Booking and security behavior

- Booking requests are checked on the server for valid dates, times, active facilities, and overlapping pending or approved bookings.
- Booking writes use a SQLite write transaction so concurrent requests are serialized for conflict checks.
- Login passwords are hashed. Protected actions use CSRF tokens, and role authorization is enforced server-side.
- Production mode requires an environment-provided `SECRET_KEY`, enables secure session cookies, and disables seeded demo-account login.

### Explainable issue triage

The local rules engine analyzes an issue title and description for configured keywords and suggests a category and priority. The admin interface shows the recommendation and its matched-term explanation. Recommendations are decision support only: they are not generated by a trained model, have not been evaluated for accuracy, and do not replace administrator judgment. An administrator's saved decision is stored separately from the reporter's submitted category and description.

## Technology

- **Backend:** Python 3.10+ and Flask
- **Database:** SQLite, accessed with Python's built-in `sqlite3` module
- **Frontend:** HTML templates rendered with Flask/Jinja and CSS
- **JavaScript:** No JavaScript files are present in the current frontend.
- **Production WSGI server dependency:** Gunicorn (used by supported WSGI hosting configurations)

The direct dependencies listed in [requirements.txt](./requirements.txt) are Flask and Gunicorn. The issue-triage engine uses Python's standard library; it does not call an external AI service or machine-learning model.

## Application structure

| Path | Purpose |
| --- | --- |
| `app.py` | Flask application factory, routes, authentication, authorization, CSRF checks, booking workflows, issue workflows, and admin analytics. |
| `db.py` | SQLite connection handling, automatic schema initialization/upgrades, local/Vercel database-path selection, and local demo-data seeding. |
| `schema.sql` | SQLite tables, constraints, foreign keys, and indexes. |
| `issue_triage.py` | Deterministic keyword-based issue category and priority recommendations with explanations. |
| `provision_admin.py` | Interactive CLI for provisioning the reserved administrator account in an initialized SQLite database. |
| `templates/` | Jinja HTML pages for login, registration, dashboards, and the application landing page. |
| `static/css/style.css` | Application styling. |
| `tests/` | Automated tests for authentication, permissions, bookings, issue reporting, analytics, provisioning, deployment settings, database paths, and triage. |
| `.env.example` | Reference environment-variable names and local defaults. The app does not load this file automatically. |

## Local installation (Windows PowerShell)

From the repository directory, create and activate a virtual environment, then install the listed dependencies:

```powershell
py -m venv .venv
.\.venv\Scripts\Activate.ps1
python -m pip install --upgrade pip
python -m pip install -r requirements.txt
```

For local development, the application defaults to `instance/campus.db`. You can leave the default configuration as-is or set an explicit path and development mode in the current PowerShell session:

```powershell
$env:APP_ENV = "development"
$env:DATABASE_PATH = (Join-Path $PWD "instance\campus.db")
```

Start the Flask development server:

```powershell
python app.py
```

On startup, the application creates the selected SQLite database directory if needed, initializes or upgrades the schema, and seeds local demo accounts and sample resources when demo seeding is enabled. There is no separate database initialization command.

Open [http://127.0.0.1:5000](http://127.0.0.1:5000). The health endpoint is `/health`. Use **Create Student Account** on the login page to register a student. Local development initializes demo users, but their passwords are intentionally not published here.

### Administrator provisioning

`provision_admin.py` is an interactive command; it does not accept a password as a command-line argument. It requires an already initialized SQLite database and uses the reserved administrator identifier configured by the application. The identifier is entered privately; the password is prompted twice without echo and must be at least 12 characters. It refuses to replace an existing account.

Run the command with `DATABASE_PATH` set to the same initialized database that the app uses:

```powershell
python provision_admin.py
```

For a production-mode database, configure `APP_ENV=production`, a stable `SECRET_KEY`, `DEMO_USERS_ENABLED=false`, and the intended `DATABASE_PATH` in the process or hosting environment **before the first application startup**. Production startup initializes the schema and sample resources but does not seed demo users. Then run the provisioning command with the same database path. Keep secret values out of source control and terminal transcripts.

## Configuration

The application reads configuration from process environment variables. It does not automatically load `.env` or `.env.example`.

| Variable | Behavior |
| --- | --- |
| `APP_ENV` | Set to `production` for hosted production behavior. |
| `SECRET_KEY` | Required in production; used to sign sessions. Store a stable secret in the hosting provider's environment settings. |
| `DATABASE_PATH` | Optional SQLite file path. Defaults to `instance/campus.db` locally. |
| `VERCEL` | When equal to `1` and `DATABASE_PATH` is unset, the default becomes `/tmp/campus.db`. |
| `DEMO_USERS_ENABLED` | Controls local demo-user seeding. Production always disables demo seeding and built-in demo login. |
| `SESSION_COOKIE_SECURE` | Optional HTTPS cookie setting for local/test configurations. Production forces secure cookies. |
| `HOST` | Local development server bind address; defaults to `127.0.0.1`. |
| `PORT` | Local development server port; defaults to `5000`. |
| `FLASK_DEBUG` | Enables Flask debug mode only when set to `true`. Do not enable in production. |

## Vercel and SQLite demo limitation

When Vercel sets `VERCEL=1` and no `DATABASE_PATH` override is configured, the app stores its SQLite file at `/tmp/campus.db`. This avoids trying to create the default `instance` directory beneath Vercel's read-only application directory.

`/tmp` is temporary storage, **not persistent database storage**. Registrations, bookings, issue reports, and other changes can disappear between invocations or deployments. Separate serverless instances may also use separate SQLite files, so users on different instances may not see the same data. This configuration is suitable only for a temporary demo; it does not provide reliable persistence or multi-instance consistency.

## Tests

Run the complete automated test suite from the repository root:

```powershell
.\.venv\Scripts\python.exe -m unittest discover -s tests -v
```

The tests cover account registration and login, role authorization, admin provisioning, booking validation and conflict handling, facility issue reporting and admin actions, analytics, deployment settings, database path selection/initialization, and issue-triage rules. This README does not assert a test result; run the command to see the current result.
